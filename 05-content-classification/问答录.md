## 学完检查参考答案

### 1. 模型输入、logits、概率和最终判断分别是什么？

输入是一批经过尺寸调整和归一化的 RGB 图片。一张图片的形状是 `[3, 224, 224]`。

模型为每张图片输出两个任意大小的分数：

```text
[normal_logit, unsafe_logit]
```

`softmax` 把它们转成总和为 1 的两个概率。程序再把 `unsafe` 概率和保存的 threshold 比较，得到 `normal` 或 `unsafe` 的最终判断。

### 2. 为什么最后一层是 `Linear(512, 2)`？

ResNet18 主干最终为每张图产生 512 个特征，所以这一层有 512 个输入。当前任务有 `normal`、`unsafe` 两个互斥类别，所以需要两个输出分数。

### 3. 冻结主干后，哪些参数会变化？

只有新建的 `model.fc` 最后一层参数会被 optimizer 更新。冻结主干的参数仍参与前向计算，但不计算和应用训练梯度。

### 4. 为什么训练可以随机增强，validation 和预测不行？

训练增强是在不改变标签的前提下制造输入变化，帮助模型减少死记硬背。validation 和预测要稳定、可复现；同一张图每次随机裁剪不同，就无法公平比较模型，也会导致接口结果抖动。

### 5. validation 做了哪两件事？

它用来比较每个 epoch 的泛化表现，并选择 threshold。本项目保存 validation F1 最好的 checkpoint，同时把该次选择出的 threshold 一并保存。

### 6. 为什么不能根据 test 反复调整 threshold？

因为每一次调整都利用了 test 答案。反复调整后，方案已经间接适配 test，test 就不能再代表未知数据。threshold 应根据 validation 选择，test 最后只做验收。

### 7. FP 和 FN 各是什么？

```text
FP：真实是 normal，模型判断 unsafe，表示误杀。
FN：真实是 unsafe，模型判断 normal，表示漏放。
```

降低 threshold 通常能减少 FN、提高 Recall，但可能增加 FP。提高 threshold 往往相反。

### 8. 为什么 checkpoint 还要保存类别映射和 threshold？

模型参数只产生数字，不说明第 0 个数字是哪一类，也不说明概率达到多少才拦截。类别映射解释输出顺序，threshold 把概率转成业务判断；缺少任意一个都可能让线上结果与训练评估不一致。

### 9. FastAPI 有没有训练模型？

没有。它只加载 checkpoint，对上传图片执行预处理和前向计算，再用 softmax 与 threshold 生成 JSON。推理阶段没有 loss、`backward()` 或 `optimizer.step()`。

### 10. 为什么多个风险类型可能是多标签？

因为一张图可以同时包含色情、暴力和武器。四选一的 softmax 强迫这些类别互斥；多标签模型为每种风险分别输出概率，更符合这种同时成立的关系。`normal` 通常可以解释为没有风险标签达到各自阈值。

## 当前项目的 threshold 是怎么定出来的？

模型先为 validation 中每张图片计算 `unsafe` 概率。代码随后依次尝试：

```text
0.10、0.15、0.20……0.85、0.90
```

对于每一个候选 threshold，都执行：

```text
unsafe 概率 >= threshold → unsafe
unsafe 概率 <  threshold → normal
```

然后计算该 threshold 下的 Precision、Recall 和 F1，选择 validation F1 最大的 threshold。

如果几个 threshold 的 F1 相同，当前代码继续按照下面的顺序选择：

```text
优先 Recall 更高的
→ 如果 Recall 仍然相同，选择更低的 threshold
```

对应代码是：

```python
return max(
    results,
    key=lambda item: (
        item["f1"],
        item["recall"],
        -item["threshold"],
    ),
)
```

每个 epoch 都会在 validation 上重新选择 threshold。项目最后保存 validation F1 最好那一轮的模型参数和 threshold。

所以 threshold 不是模型通过 backward 学到的参数，而是模型训练后，在 validation 上比较出来的决策规则。真实业务也不一定必须选择 F1 最大值：更怕漏放时可以优先满足 Recall，更怕误杀时可以优先满足 Precision。

## `sexual / violence / weapon / normal` 怎样扩展成多标签？

一张图片可能同时包含色情、暴力和武器，因此不适合使用四选一的 softmax。更自然的标签是三个独立的是非问题：

```text
sexual  是否存在？
violence 是否存在？
weapon   是否存在？
```

每张图片的标签变成长度为 3 的向量：

```text
[0, 0, 0] → 没有风险，解释为 normal
[1, 0, 0] → sexual
[0, 1, 1] → violence + weapon
[1, 1, 1] → 三种风险同时存在
```

`normal` 最好不要作为第四个独立标签，否则可能出现自相矛盾的数据：

```text
normal=1，同时 sexual=1
```

模型最后一层从：

```python
nn.Linear(512, 2)
```

变成：

```python
nn.Linear(512, 3)
```

它输出三个互不排斥的 logits：

```text
[sexual_logit, violence_logit, weapon_logit]
```

这里不再使用 softmax，而是给每个 logit 分别做 sigmoid：

```text
sexual_probability  = sigmoid(sexual_logit)
violence_probability = sigmoid(violence_logit)
weapon_probability   = sigmoid(weapon_logit)
```

三个概率不要求相加等于 1，所以可以同时超过各自 threshold。训练时使用：

```python
nn.BCEWithLogitsLoss()
```

而不是当前互斥分类使用的 `CrossEntropyLoss`。

每个标签可以有自己的 threshold：

```text
sexual  >= 0.40 → 命中 sexual
violence >= 0.55 → 命中 violence
weapon   >= 0.60 → 命中 weapon
三个标签都没有命中 → normal
```

这些 threshold 分别在 validation 上选择，指标也要分别计算。数据不能再只靠 `normal/unsafe` 文件夹表达，需要为每张图片保存类似下面的标注：

```text
image_001.jpg, sexual=1, violence=0, weapon=1
```

当前二分类数据只有 `normal/unsafe`，不能直接训练出 violence 和 weapon。必须重新收集或标注包含这三个字段的数据。

## 卷积是什么？

卷积可以先理解成一个很小的“局部观察器”。例如一个 `3×3` 卷积核，每次只观察图片中的 `3×3` 小区域：

```text
原图的一小块 3×3 像素
→ 每个像素乘上卷积核中的权重
→ 把结果加起来
→ 得到当前位置的一个数字
```

这个小观察器会从左到右、从上到下滑过整张图片：

```text
┌───────────────┐
│ [3×3] →       │
│       [3×3] → │
│               │
└───────────────┘
```

同一组卷积核参数会在图片所有位置重复使用。因此，一个学会识别竖线的卷积核，不论竖线出现在左边还是右边，都可能产生响应。

训练之前，卷积核里的权重只是一组初始数字。训练过程中仍然通过：

```text
forward → loss → backward → optimizer.step()
```

逐渐学出有用的局部特征。通常可以粗略理解为：

```text
浅层卷积：边缘、颜色、简单纹理
中层卷积：轮廓、局部形状
深层卷积：更复杂的物体部件和组合
```

ResNet18 的主干包含很多卷积层。它们最终把 `[3, 224, 224]` 的图片逐步转换成 512 个高级特征，再交给 `fc` 分类层。

卷积和裁剪不是一回事：

```text
裁剪：删除图片的一部分
卷积：在保留的输入上滑动计算并提取局部特征
```

## 这次训练使用 GPU 了吗？

使用了。训练日志中有：

```text
device=mps
```

`mps` 是 Apple 的 Metal Performance Shaders，表示 PyTorch 把模型和 batch 放到了 Mac 的 Apple GPU 上计算。它不是 NVIDIA 的 CUDA，但同样属于 GPU 加速。

当前设备选择顺序是：

```text
有 CUDA → 使用 NVIDIA GPU
否则有 MPS → 使用 Apple GPU
否则 → 使用 CPU
```

训练时，图片预处理和 DataLoader 主要仍在 CPU 上运行；模型的 forward、loss、backward 和参数更新在 MPS 设备上执行。由于当前 `frozen_backbone=True`，GPU 会执行整个 ResNet18 的 forward，但只有新 `fc` 层需要计算并更新训练梯度。

## 随机裁剪和 CenterCrop 会不会丢失信息？内容审核应该怎样处理？

会。裁剪一定可能删除图片信息。

训练时的 `RandomResizedCrop` 会随机选择原图的一部分，再缩放到 `224×224`。它可以让模型适应位置和大小变化，但如果违规内容只位于角落，裁剪后可能出现：

```text
模型看到的图片已经没有违规内容
标签却仍然是 unsafe
```

这会制造标签与实际输入不一致的训练样本。

validation、test 和推理使用的 `CenterCrop` 不随机，但它只保留中心区域。尤其对于长图或宽图，左右或上下可能被删除很多。它的优点是结果固定、符合 ResNet 常见的预训练输入方式，缺点是边缘风险内容可能完全消失。

可以考虑下面四种处理方式：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 整张图直接缩放到 `224×224` | 不丢内容 | 可能拉伸变形 |
| 保持宽高比，空白补边成正方形，再 Resize | 不丢内容，也不拉伸 | 目标在输入中可能变小 |
| 整图预测，再对多个局部区域预测 | 既看全图，也能发现角落小目标 | 推理次数增加 |
| 使用更高分辨率或目标检测模型 | 更适合发现局部风险 | 训练和推理成本更高 |

对于当前内容审核项目，优先建议：

```text
保持原图宽高比
→ 空白补边成正方形
→ Resize 到 224×224
```

它不是所有场景下的唯一正确答案，但比 CenterCrop 更适合作为“不遗漏边缘内容”的第一版基线。之后再根据 Bad Case 判断是否需要多区域预测或更高分辨率。

分析 Bad Case 时还要注意：当前 HTML 报告展示的是完整原图，模型实际看到的却是 CenterCrop 后的 `224×224`。因此更可靠的报告应该同时展示“原图”和“模型实际输入”。


## 迁移学习是不是模型已经训练好了？

一半是，一半不是。

ResNet18 主干已经在 ImageNet 图片上训练过，具备通用视觉特征提取能力；但它原来的任务不是我们的 `normal / unsafe`。我们替换并训练最后一层，让通用特征服务于当前任务。

## 为什么 `model.fc` 是 ResNet18 的最后分类层？

不是 Python 根据位置自动判断出了“最后一层”，而是 Torchvision 在定义 ResNet18 时，明确把最后的全连接分类层命名为 `fc`。

模型末尾大致是：

```text
卷积层和残差层
→ avgpool
→ flatten
→ fc
```

打印模型时可以看到：

```text
(fc): Linear(in_features=512, out_features=1000)
```

因此：

```text
model.fc              ResNet18 原来的最后分类层
model.fc.in_features  分类层接收的特征数量，也就是 512
model.fc.out_features 原来输出的类别数量，也就是 1000
```

执行：

```python
input_features = model.fc.in_features
model.fc = nn.Linear(input_features, 2)
```

就是先记住旧分类层接收 512 个特征，再用新的 `Linear(512, 2)` 替换它。ResNet18 的 forward 本来就会在最后执行 `self.fc(x)`，所以不需要修改 forward。

其他模型的分类层不一定叫 `fc`：

```text
ResNet18     model.fc
EfficientNet model.classifier
ViT          model.heads
```

## 为什么把 epochs 从 5 改成 15、batch size 改成 64，效果没有明显提升？

先看最终 test：

| 设置 | Precision | Recall | F1 | FP | FN |
|---|---:|---:|---:|---:|---:|
| 5 epoch | 0.902 | 0.948 | 0.925 | 16 | 8 |
| 15 epoch、batch 64 | 0.891 | 0.948 | 0.919 | 18 | 8 |

第二次并不是明显退化。test 只有 293 张图，主要差别只是多误杀了 2 张 normal 图片，F1 相差 `0.006`。这么小的 test 集上，少数图片就会让指标发生肉眼可见的变化。

### 原因一：epoch 更多，不代表参数更新次数一定更多

训练集有 2,178 张图。每个 epoch 的更新次数约等于：

```text
训练样本数 ÷ batch size
```

如果第一次使用默认 `batch_size=16`：

```text
每个 epoch：2178 ÷ 16 ≈ 137 次更新
5 个 epoch：约 685 次更新
```

第二次使用 `batch_size=64`：

```text
每个 epoch：2178 ÷ 64 ≈ 35 次更新
15 个 epoch：约 525 次更新
```

所以虽然第二次看了 15 遍数据，optimizer 实际执行 `step()` 的次数反而可能更少。batch size 主要影响一次用多少样本估算梯度、每个 epoch 更新多少次以及训练速度，它不是越大效果越好。

### 原因二：当前只训练最后一层

日志显示：

```text
frozen_backbone=True
```

这表示 ResNet18 主干全部冻结，训练过程中只更新新的：

```text
Linear(512, 2)
```

这个线性分类层很快就会接近它在固定特征上能达到的上限。继续增加 epoch，只是在微调同一条分类边界；如果冻结的 ImageNet 特征无法很好地区分某些色情和正常图片，最后一层训练更久也解决不了。

### 原因三：validation 已经进入平台期

第二次训练中，validation F1 从第 6 个 epoch 左右开始主要在：

```text
0.872～0.887
```

之间波动。第 5 个 epoch 的 `0.867` 到第 15 个 epoch 的 `0.887` 只有小幅提升。这说明模型仍有一点收益，但已经没有明显的持续增长。

更多 epoch 只能让 optimizer 继续尝试，不能保证 validation 或 test 一定提高。选择最佳 checkpoint 的依据仍然应该是 validation，而不是“最后训练到了多少轮”。

### 原因四：两次模型使用了不同 threshold

第一次最佳模型使用：

```text
threshold=0.60
```

第二次使用：

```text
threshold=0.50
```

所以最终指标不仅取决于模型参数，也取决于 validation 选择出的 threshold。两次 Recall 都是 `0.948`，第二次多了 2 个 FP，因此 Precision 和 F1 略低。

### 这次实验应该得到什么结论？

不能得出“15 epoch 没用”，也不能得出“batch size 64 更差”。因为你一次同时修改了两个变量，无法判断变化究竟来自哪一个。

下一次应该只改一个变量：

```text
实验 A：batch_size=16，epochs=5
实验 B：batch_size=16，epochs=15
```

或者：

```text
实验 A：batch_size=16，epochs=15
实验 B：batch_size=64，epochs=15
```

都使用相同的数据划分和 learning rate，然后先比较 validation。test 只在最终选定方案后查看一次。

当前结果更可能说明：只训练最后一层已经接近瓶颈。下一步比继续增加 epoch 更有价值的是查看 FP/FN Bad Case，判断问题来自标签、数据覆盖、threshold，还是固定的 ResNet 特征确实不够；之后再考虑用较小 learning rate 解冻主干进行微调。

## 三份 Bad Case 报告说明了什么？还应该继续增加 epoch 或修改 batch size 吗？

三份 validation 报告的结果是：

| 设置 | Threshold | FP | FN | 总误判 | Validation F1 |
|---|---:|---:|---:|---:|---:|
| 5 epoch / batch 16 | 0.60 | 22 | 15 | 37 | 0.885 |
| 15 epoch / batch 64 | 0.50 | 21 | 15 | 36 | 0.888 |
| 15 epoch / batch 16 | 0.45 | 28 | 10 | 38 | 0.886 |

三者的 F1 最大只相差约 `0.003`，误判总数也几乎相同。进一步比较全部错误图片：

```text
三个模型都判断错误：29 张
其中共同 FP：20 张
共同 FN：9 张
三个模型所有错误的并集：46 张
```

这说明大部分错误稳定地出现在同一批图片上。主要瓶颈更可能是：

```text
标签规则模糊或标签有噪声
normal / unsafe 的视觉范围太宽
每个类别主要来自少数连续数据分片
裁剪后关键信息丢失
冻结的 ResNet 特征不足以识别商品、文字或隐晦语义
```

因此，当前不建议继续盲目尝试更多 epoch 或不同 batch size。更合理的顺序是：

```text
1. 人工复查三个模型共同判断错误的 29 张图片
2. 区分标签错误、规则有争议、裁剪问题和真正的模型错误
3. 修正标签，并从多个数据分片补充有针对性的 Hard Case
4. 用补边方案替换 CenterCrop，保持其他条件不变做对照实验
5. 再考虑用较小 learning rate 解冻 ResNet 后部进行微调
```

先解决标签、采样来源和裁剪问题，预期收益通常会比把训练从 15 epoch 增加到 30 epoch 更明显。

## 模型给出的 0.92 就代表有 92% 的把握吗？

不能直接这样保证。softmax 输出可以用作模型分数和类别间的相对概率，但神经网络可能过度自信。真实上线前还需要在代表性 validation 数据上检查概率校准，并结合错误成本选择 threshold。

本章先把它读作“模型为 unsafe 分配了 0.92 的概率分数”，不要把它解释成现实世界中严格准确的 92% 可信度。

## F1 最好就一定能上线吗？

不一定。F1 把 Precision 和 Recall 合成一个数，但没有表达不同错误的业务成本，也可能掩盖某些人群、场景或风险子类型上的失败。

内容审核通常还要分别规定 Recall、误杀率、特定风险类别指标、延迟和人工复核策略，并持续查看 Bad Case 与数据分布变化。
